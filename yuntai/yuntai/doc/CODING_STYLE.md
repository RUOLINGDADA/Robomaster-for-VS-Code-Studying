# 代码与注释规范

本文件补充 `AGENTS.md`，目标是让 STM32 初学者可以沿着注释理解代码，同时让熟悉嵌入式的开发者能快速定位协议、时序和资源边界。

## 双轴快照与 DMA 日志

Yaw 和 Pitch 使用同一套轴无关控制组合，但每个轴必须有自己的句柄、配置和测试状态。
控制周期先通过 `Gm6020_GetSnapshot()` 复制完整反馈，角度环、堵转保护和该周期日志都
引用这份快照；不能在日志中再直接读取 CAN ISR 可能正在更新的句柄字段。USART DMA 发送
必须保留发送缓冲区直到完成回调，串口繁忙时直接返回，不能在控制任务中忙等。

## 注释的五个层次

### 0. 先写设计理由，再写白话解释

关键注释按“做什么、为什么这样做、换一种看似直观的写法会怎样”说明。专业术语、协议字段和单位必须保留，后面紧跟括号式白话解释。例如限位使用连续总角度，是因为它是展开后的线性坐标；单圈角度在 `8191→0` 回绕，直接比较大小会把正常跨圈误判为越界（白话：单圈像钟表，不能拿钟表的数字直接判断机械位置）。

注释应解释真实的设计取舍：坐标系、快照一致性、启动/换向宽限、输出限幅、DMA 缓冲区所有权和失败后的安全状态。不要只写“设置变量”“进入状态”，也不要为每行明显赋值制造空泛说明。

### 1. 文件级多行注释

每个自建源文件和头文件开头都要说明：文件属于哪个模块、负责什么、使用哪些硬件或协议、运行在任务/普通调用/中断中的哪一种上下文，以及明确不负责什么。

```c
/**
  ******************************************************************************
  * @file    can_motor_protocol.c
  * @brief   RoboMaster 电机 CAN 反馈帧解析和控制帧打包。
  *
  * 本文件只处理 CAN 标准帧的 ID、字节序和数据字段，不创建任务，
  * 不直接决定电机是否允许运行。接收入口可能由 CAN ISR 调用，
  * 因此这里不能调用会阻塞的 FreeRTOS API 或打印大量日志。
  ******************************************************************************
  */
```

文件级注释不是版权模板的替代品，而是给后来维护者的使用边界。

### 2. 函数级多行注释

公共函数必须写清参数、返回值、单位、调用上下文和失败后的状态。每个自有源文件中未在头文件声明的函数（包括 `static` 辅助函数）也必须有紧邻的用途注释；简单的限幅、查找和名称转换写短说明，复杂私有函数再说明核心前提、处理顺序、设计原因和失败出口。HAL/CubeMX 官方模板不在本规则改写范围内。

```c
/**
 * @brief  从一帧 8 字节反馈数据更新电机快照。
 * @param  hmotor 电机句柄，必须已经完成初始化。
 * @param  data   CAN DATA[0] 到 DATA[7]，长度必须为 8 字节。
 * @retval true   数据已解析并刷新 last_feedback_ms。
 * @retval false  参数为空或句柄未初始化。
 *
 * @note   CAN 协议字段按大端排列；STM32F407 使用小端内存布局，
 *         不能把两个字节直接转换成 int16_t 指针后读取。
 * @note   本函数不判断电机是否超时，超时由任务上下文中的
 *         CanMotor_Process() 根据 HAL_GetTick() 判断。
 */
bool CanMotor_ParseFeedback(CanMotor_HandleTypeDef *hmotor,
                            const uint8_t data[8]);
```

### 3. 代码块多行注释

状态机、初始化顺序、资源清理、DMA 双缓冲和协议解析要在代码块前解释先后关系和原因。

```c
/*
 * 初始化顺序不能交换：
 * 1. 先配置 GPIO 和 SPI 片选，避免设备在上电后处于错误模式；
 * 2. 再读取芯片 ID，确认总线确实连到目标器件；
 * 3. 最后写量程和带宽寄存器。
 * 如果跳过第 2 步，SPI 线断开时写配置也可能返回 HAL_OK，
 * 但后续读取永远是无效数据。
 */
```

### 4. 单行注释

单行注释紧贴具体语句，解释底层坑点或单位，不重复代码含义。

```c
header.DLC = 8U; /* C620 控制帧固定 8 字节，不能用 sizeof(data) 替代协议约定。 */
data[0] = (uint8_t)(current_raw >> 8); /* 协议是大端：高字节先发。 */
```

不推荐：

```c
/* 设置 DLC */
header.DLC = 8U;
```

因为它没有解释 8 的来源和修改风险。

### 5. 失败出口注释

使用 `goto` 统一释放资源时，在标签前说明清理顺序和为什么多个路径共享该出口：

```c
init_failed:
  /* 先关闭 DMA，再释放片选和状态标志，避免中断继续访问半初始化对象。 */
  Bmi088_Port_StopDma(hbmi088);
  hbmi088->initialized = false;
  return false;
```

## 必须解释的底层主题

以下代码出现时，注释中必须至少解释对应的风险：

| 代码主题 | 必须解释的内容 |
|---|---|
| `volatile` | 只保证每次从内存读写，不保证多字段原子性、线程安全或事件不丢失 |
| ISR | 只能做短操作；FreeRTOS 必须使用 `FromISR` 接口，并说明唤醒任务的处理 |
| DMA | 缓冲区生命周期、缓存一致性（如适用）、完成标志和重复启动条件 |
| `memcpy`/指针转换 | 对齐、大小端、结构体填充和长度边界 |
| 寄存器位操作 | 位编号、读改写风险、写 1 清零或写保护要求 |
| `static` | 文件私有性、静态存储期，以及它是否位于 `.bss`/`.data` |
| `const` | 是否只读、是否可能放入 Flash，以及调用者能否修改对象 |
| FreeRTOS 延时 | `vTaskDelay` 与 `vTaskDelayUntil` 的周期差异和 Tick 单位 |
| Tick 计算 | 说明时钟来源和单位；短时间间隔用同类型无符号差值处理回绕，不混用 HAL 毫秒与 FreeRTOS Tick |
| 电机保护 | 目标指令与实际反馈的区别、阈值依据、持续时间、停止与恢复条件、解除后的任务阶段，以及忽略其中一项会怎样误判 |
| 数值转换 | 单位、缩放、饱和、负数和 `INT16_MIN` 等边界 |
| 临界区 | 保护哪些共享字段、持续多久、是否可能在 ISR 中使用 |

## 面向初学者的写法

- 首次出现的缩写给出全称，例如 ISR（Interrupt Service Routine，中断服务程序）、DMA（Direct Memory Access，直接内存访问）。
- 协议字段使用 `DATA[0]`、`StdId` 等实际名称，并同时写清物理意义和单位。
- 不把重要逻辑藏在复杂宏中；需要类型检查或多步处理时使用 `static` 函数。
- 对硬件初始化写出顺序；对任务写出周期、阻塞点和优先级依据；对队列写出元素类型和长度。
- 解释不能这样改的地方。例如不能在中断里调用 `printf`、不能在 DMA 仍运行时复用缓冲区、不能把角度误差直接相减。

## 宏定义注释

项目自建和新增的每个 `#define` 都必须带注释。注释至少说明以下一项：

- 时间宏：单位是毫秒、FreeRTOS Tick 还是秒，以及它用于阶段、超时还是日志限频；
- CAN 宏：标准帧 ID、反馈/控制方向和对应电机槽位；
- 电机参数宏：原始值、正负方向和是否只是台架调试起点；
- 算法宏：物理单位、增益含义、范围或滤波系数约束；
- 头文件保护宏：说明它用于防止重复包含。

多行宏的注释放在宏前或最后一行表达式后，不能把反斜杠后的文字误当成宏内容。CubeMX/HAL/FreeRTOS 自动生成宏可以保留官方注释；如果修改其值，必须补充工程影响说明。

控制器调参配置头文件必须在参数宏附近提供“现象 → 调什么 → 为什么”的速查表。至少说明电机不动、动作过慢、过冲或振荡、持续静差、电流换向冲击、反馈噪声、堵转误判和软件限位无法恢复时的首选参数及副作用；这样使用者可以先按现象定位，避免同时乱改多个增益。

## 长度控制

- 小型 HAL 适配文件通常控制在 150 至 400 行；超过 500 行时检查是否混入了协议、业务或测试逻辑。
- 协议文件可因字段较多达到 500 至 1000 行，但应按帧类型分段并有目录式块注释。
- 单个函数通常不超过 80 行；初始化或状态机超过 120 行时拆成有明确职责的私有函数。
- 注释可以占源文件的 20% 至 40%。底层驱动和教学性代码宁可多解释关键机制，也不要用无意义的逐行翻译填充长度。
- 注释不能代替文档。跨文件的时序、任务关系、引脚表和协议完整定义放到 `doc/`。

## 修改检查清单

提交前逐项检查：

- 新文件是否有文件级多行说明？
- 公共函数是否写了参数、返回值、单位和调用上下文？
- 是否对大小端、ISR、DMA、volatile、Tick、临界区和边界值做了必要解释？
- 单行注释是否解释了真正的坑点，而不是复述代码？
- 是否说明了失败路径、清理顺序和硬件状态？
- 是否把跨模块信息同步到了 `doc/`？
- 修复 Bug 后，是否在 `AGENTS.md` 和 `doc/BUG_FIXES.md` 记录了根因、防复发检查与实际验证范围？
- 涉及超时或电机保护时，是否检查了时间来源、反馈有效性以及完整的进入/停止/恢复路径？

## 硬件测试文件写法

- 永久硬件测试与驱动同级，放在 `Core/Inc/bsp/<driver>/`、`Core/Src/bsp/<driver>/`；禁止建立统一 `Core/Inc/test/`、`Core/Src/test/` 目录。
- 只保留能够烧录后直接观察硬件行为的测试。协议解析、PID、Ramp、回绕和限幅等纯逻辑由 agent 用临时脚本验证，不把临时验证代码提交到工程。
- 硬件测试文件使用 `test_<driver>_<feature>.h/.c` 命名。头文件必须说明初始化顺序、真实硬件要求、参数单位、调用上下文、输出状态和急停限制。
- 硬件测试必须调用正式驱动和正式控制算法，不得复制一套测试 PID、CAN 发送或保护状态机；用户调出的参数应能直接进入正式配置。
- 测试函数必须非阻塞、可重复周期调用，每次只执行一个控制步；不能使用 `HAL_Delay`，不能在 CAN ISR 中打印或调用普通 FreeRTOS API。
- 任务入口只保留一个直接硬件测试调用和一个正式路径分支，不使用测试套件枚举来同时管理多个会写电流的测试。
- 持续硬件日志使用中文并限频；GM6020 角度测试至少输出目标角度、实际角度、误差、速度、电流、输出许可、限位和保护原因。

## 同型号多实例、周期快照与诊断

- 可复用控制、保护与组合逻辑放 app/gimbal，任务只保存本轴配置、命令适配和调度入口；共用模块不能包含 Yaw/Pitch 任务头文件或调用全局 Yaw 命令。
- 每轴电机、PID、Ramp、滤波、保护、测试提示和日志计时分别保存；同型号多实例不得共享文件级可变运行状态。
- 测试和正式路径每周期只取一次 Gm6020_GetSnapshot。该份反馈贯穿计算、保护与日志；保护使用本周期的电流请求，不用旧输出许可替代当前意图。
- 日志区分控制器计算电流、保护后目标电流、输出许可和 CAN 提交；许可与提交都不能证明电调已经执行。保护事件保存触发周期现场，串口忙时重试该份记录。
- 标定日志必须显示轴名称、零电流、中位和两侧限位记录提示；程序不自动宣布步骤完成，最终 min/max 按实测连续计数排序。
- 固定目标不是遥控松手，不能以零速度命令、电流下降或等待时间单独恢复堵转。恢复检查反向实际位移、范围、新鲜反馈、电流下降和持续时间，掉线不能清锁。
- 时间戳 0 ms 可以是真实首帧，需独立的有效标志；用无符号差值处理短周期回绕。反馈更新略晚于任务 now_ms 时不能误判成巨大的超时。
- 首帧只要求启动位置相对标定中心可由半圈内最短差值唯一解释，不把机械总行程限制为半圈。
- USART 使用非阻塞接受接口、int 格式化长度和 DMA 完成前保持不变的缓冲区；忙时下一周期重试。整数拼接小数目标角度兼容 newlib-nano，无需开启浮点 printf。
