# yuntai 项目规则

## 适用范围

本文件适用于当前目录及其所有子目录。修改本工程前，先阅读本文件和 `doc/README.md`；再根据任务阅读 `doc/` 下的相关专题文档。父目录中的其它示例工程不属于本项目修改范围。

## 项目目标与技术基线

- 目标平台：STM32F407，HAL，C11，CMake，arm-none-eabi-gcc。
- 系统基础：FreeRTOS。任务、队列、信号量、软件定时器和事件组按实际功能添加，不为了形式完整而增加对象。
- 当前工程入口：`Core/Src/main.c`、`Core/Src/freertos.c`、`CMakeLists.txt` 和 `cmake/stm32cubemx/`。
- 参考风格：`../can_example`。优先保持其命名、目录、头文件保护、注释语言和模块拆分方式；不复制与当前功能无关的复杂错误回调体系。

## 目录与模块边界

采用多文件夹、多层级的模块化结构。一个较大的设备驱动对应一个目录；小功能也可以按功能单独成目录。

```text
Core/
  Inc/                         # 公共头文件、CubeMX 生成头文件
    bsp/<driver>/              # 设备驱动头文件
    app/<feature>/              # 应用功能头文件
  Src/
    bsp/<driver>/              # 设备驱动源文件
    app/<feature>/              # FreeRTOS 任务或应用逻辑
doc/                           # 工程对接、协议、决策和变更记录
```

- 驱动目录按设备或外设命名，例如 `bsp/c620/`、`bsp/imu/`、`bsp/uart/`。
- 应用目录按功能命名，例如 `app/gimbal/`、`app/remote/`、`app/chassis/`。
- 一个模块公开一个主头文件，内部辅助函数和状态尽量保留在 `.c` 文件中。
- 模块之间通过公开 API、数据结构和 FreeRTOS IPC 通信，不直接访问其它模块的 `static` 数据。
- 不因为目录规则机械拆分只有几行且不会复用的代码；拆分应降低依赖和便于替换。

### 当前任务目录约束

- 每个 FreeRTOS 任务使用独立目录：`Core/Inc/task/<task_name>/` 与 `Core/Src/task/<task_name>/`；入口只负责初始化与周期调度，配置和命令适配按需保存。多轴可复用的控制、保护和运行时放在 `app/gimbal/`，不要为了目录形式在任务下复制一套实现。
- 供弹任务也必须遵守同样的拆分：`task_feed_motor.c` 只调度，`command/control/protection/runtime` 分别保存测试配置、阶段状态机、安全策略和硬件组合；不能把所有逻辑重新塞回入口文件。
- `freertos.c` 只保留 CubeMX 创建、属性和 `__weak` 安全兜底；业务强入口放在任务目录，并在顶层 CMake 中显式列出。
- 供弹阶段时长、日志间隔等配置统一以毫秒保存；与 `TickType_t` 比较前必须在使用点调用 `pdMS_TO_TICKS()`，禁止利用当前 1 kHz 配置直接把毫秒数当 Tick 数。
- `task_yaw` 只控制水平 Yaw 轴；`task_pitch` 只控制纵向 Pitch 轴；两个 GM6020 必须使用独立句柄。供弹电机只有一个，目录迁移不能复制出第二个实例。
- Yaw 正式流程是相对速度命令、目标角度保持、角度 P/速度 PI、电流 Ramp、软件边界和可恢复堵转保护；固定左右电流自循环只能作为单独测试模式，不能混入正式任务入口。
- GM6020 通用驱动不判断动态物理堵转。堵转由 `app/gimbal/gimbal_protection` 判断，并同时使用目标电流、实际反馈电流、速度、位置变化、反馈新鲜度、启动/换向宽限和输入意图。Yaw/Pitch 正式模式与硬件测试调用同一个 `GimbalAxis` 运行时。
- `Gm6020_GetSnapshot()` 是任务与硬件测试读取反馈、状态的强制入口；禁止任务直接拼接 CAN ISR 可能正在更新的多个句柄字段。

### 硬件测试与调参规则

- 永久保留的测试代码必须与被测驱动同级：GM6020 放在 `Core/Inc/bsp/gm6020/`、`Core/Src/bsp/gm6020/`，C610/M2006 放在对应驱动目录；禁止重新建立统一 `Core/Inc/test/`、`Core/Src/test/` 测试目录。
- 只提交真正需要烧录上板的硬件测试，例如 GM6020 角度标定、固定目标角度保持和 C610 供弹自循环；反馈解析、PID、Ramp、回绕、钳位等纯逻辑由 agent 使用临时脚本或临时主机程序验证，验证后不提交。
- 测试文件使用 `test_<driver>_<feature>.h/.c` 命名。每个测试头文件必须说明硬件需求、初始化顺序、参数单位、调用上下文、输出行为和安全限制。
- 硬件测试必须直接复用正式驱动和正式算法，不得复制另一套 CAN 解析、PID、Ramp、限位或堵转保护；调参结果必须能够直接写入正式配置。
- 硬件测试函数必须是非阻塞单步函数，每次任务调用只推进一个周期；不能调用 `HAL_Delay`，不能在 CAN ISR 中打印、等待或调用普通 FreeRTOS API。
- 每个电机任务最多保留一个简单的硬件测试模式分支；同一周期只能由测试路径或正式路径其中一个写入电流，不能使用测试套件同时分发多个会写电流的测试。
- Yaw/Pitch 测试分为“只读手动标定”和“固定目标角度闭环”两种模式。标定模式强制零电流；角度环模式使用已记录的中心、最小和最大连续角度，目标角度以中心为参考，用户只修改带单位注释的配置宏。
- 标定数据必须记录来源和实测状态。未完成标定时正式控制保持零输出，不能回退到未经确认的临时范围继续驱动。
- GM6020 角度环硬件测试必须输出目标角度、实际连续角度、误差、目标速度、实际速度、目标电流、反馈电流、输出许可、限位和保护原因；日志只能在任务上下文使用中文输出。
- GM6020 标定和固定目标测试必须使用轴无关接口，参数通过 `Gm6020_CalibrationTypeDef` 和各轴独立配置传入；Yaw/Pitch 不得复制测试算法或共享测试状态。
- 测试和通用轴运行时每个控制周期只取得一份 `Gm6020_GetSnapshot()` 快照，控制、保护和日志必须引用同一份快照；不得在日志中混读句柄字段或重新取下一帧拼接数据。
- 标定日志必须说明零电流状态，并提示中位、左/右或下/上物理边界的记录操作；最小/最大值最终按实测连续计数排序；程序不自动假定用户已经完成任何一步。
- 固定目标测试进入堵转保持后，不能把零命令当作释放条件；默认必须检测实际位置向堵转反方向移动约 5 度且反馈电流下降，再经过确认时间才恢复。
- USART DMA 日志发送必须非阻塞，使用原子操作取得缓冲区所有权，DMA 完成回调后才释放；不能覆盖缓冲区、忙等或因日志繁忙触发 Error_Handler。格式化长度使用 `int`，超长文本整条拒绝以免截断中文；重要提示使用可返回接受结果的接口重试。

- 固定目标测试确认堵转后，必须向触发方向的反方向移动配置距离、仍处于标定范围内、反馈新鲜且电流下降，连续满足恢复时间后才能解除；CAN 掉线不能清掉已锁存的堵转，也不能累计掉线时间作为恢复证据。
- 电流聚合帧的“读取全部电机槽位 → 构建 → 提交 HAL 邮箱”必须在同一个短临界区完成，防止任务切换提交旧帧；临界区内禁止等待或打印。软件硬限位只能阻止向外电流，不得阻止向内脱离边界。
- 日志明确区分“控制器计算电流”“保护后的目标电流”“输出许可”和“CAN 已提交”；HAL 接受不等于电调实际执行。所有反馈字段必须有快照有效性和反馈年龄。
- 堵转保护的本周期驱动力判断必须使用控制器当前请求，不能拿周期开始前快照的旧输出许可替代；反馈仍只取本周期唯一快照，保护后的许可写入独立周期结果。
- 首帧标定参考要求启动位置相对中心位于可唯一解释的半圈内；禁止误写为“机械总行程必须小于半圈”。时间戳 0 ms 可能是真实反馈，不得单靠零时间戳判定离线。

### 宏定义注释规则

- 每个自建或本次新增 `#define` 都必须在同一行或紧邻上一行写明用途、单位、协议来源或边界；时间宏必须写 `ms`/`Tick`，电流宏必须写原始值，CAN ID 宏必须写标准帧含义。
- 不同电机型号的电流原始值范围必须分开核对：GM6020 电流控制按官方手册使用 `[-16384, 16384]`，C620/3508 使用 `[-16384, 16384]`，M2006/C610 使用 `[-10000, 10000]`；禁止按“都是 int16_t”复用限值。GM6020 还必须区分电流控制帧 `0x1FE/0x2FE` 与电压控制帧 `0x1FF/0x2FF`。
- 头文件保护宏也要说明“防止重复包含”；不要留下只有名字、没有解释的项目宏。
- CubeMX/HAL/FreeRTOS 自动生成宏保留官方注释；如果 agent 修改其数值，必须补充修改原因和影响到 `doc/CHANGELOG.md`。
- CAN 反馈字段也必须按具体型号手册逐字节核对；不能因为多个 RoboMaster 电机都使用 8 字节帧，就把 `DATA[6]` 一律当温度或把 `DATA[7]` 一律当错误码。保留字节只能原样记录，不能参与保护判断。

## 命名与代码风格

- 文件名、目录名使用小写英文和下划线；类型使用 `PascalCaseTypeDef`；函数使用 `Module_Action`；宏使用 `MODULE_NAME`；枚举值使用 `MODULE_STATE_xxx`；静态文件级对象使用 `g_` 前缀。
- 头文件使用 `#ifndef`/`#define`/`#endif` 保护；公共接口放头文件，私有实现放源文件。
- 缩进和大括号参照 `can_example`，使用 2 个空格缩进，函数和结构体字段按功能分组。
- 注释要让没有 STM32 经验的读者能够理解硬件发生了什么、代码为什么这样写、改动会影响什么。必须说明意图、协议来源、单位、时序、内存/中断上下文和边界条件。
- 注释采用多种层次：文件头多行注释说明模块职责；函数多行注释说明参数、返回值和调用上下文；代码块多行注释解释状态机、协议帧、资源清理等整体思路；关键行使用单行注释标出寄存器位、字节序、单位换算和容易踩坑的地方。
- 注释不要求机械解释每一行，但凡涉及底层行为或容易被小白误改的代码，都要解释原因。例如 `volatile` 的可见性边界、`FromISR` API、DMA 缓冲区、结构体对齐、大小端、整数溢出、Tick 溢出、临界区和清零时机。
- 变量名体现单位或范围，例如 `timeout_ms`、`angle_deg`、`current_raw`；避免没有上下文的 `temp`、`data1`、`flag2`。
- 优先使用明确的返回值和简单控制流。功能已经明确且能保证资源释放时，可以使用 `goto` 统一失败清理；不要为了“结构化”引入多余层级。
- 中断回调只做必要的硬件/事件记录；耗时工作、日志和业务处理放到 FreeRTOS 任务或主循环。
- 只保留与功能有关的回调。不要为每一种理论错误创建空回调；错误处理采用返回值、状态字段或单个必要的故障通知即可。

### 注释最低要求

- 每个自建 `.c`/`.h` 文件有文件级多行说明，写明模块作用、硬件接口或协议范围、运行上下文和不负责的内容。
- 每个公开函数有多行说明，至少包含 `@brief`、参数、返回值；涉及单位、任务/ISR 限制、线程安全和失败后状态时必须明确写出。
- 每个复杂函数至少有一段“先做什么、为什么这样做、失败如何退出”的块注释；资源释放和统一失败出口可以使用 `goto`，并在出口前说明清理顺序。
- 单行注释放在具体语句后或语句前，只解释该行的底层坑点，不重复函数名。例如 `/* CAN 反馈为大端，STM32 内存本身按小端解释，不能直接 memcpy 到 int16_t。 */`。
- 注释中的数值要带单位或协议含义；不要只写“延时”“限制”“状态”。
- 驱动公开和内部结构体的每个成员都必须有就地注释，至少说明单位、协议字节、有效范围、初始化状态或 ISR/任务访问上下文；不能只给结构体整体写说明而让成员靠猜。
- 如果注释描述的是数据手册、CubeMX 配置或实测结论，要写来源或验证方式；不确定内容写入 `doc/OPEN_QUESTIONS.md`。

## FreeRTOS 使用规则

- 每个任务有明确职责、周期/阻塞条件、栈大小和优先级依据。周期任务使用 `vTaskDelayUntil` 或等价的 CMSIS-RTOS 接口保持周期。
- 任务间优先使用队列、通知、事件组或信号量传递事件；避免用大量全局 `volatile` 标志拼接协议。
- ISR 中只能调用带 `FromISR` 后缀的 API，并正确处理 `higher_priority_task_woken`。
- 任务入口不得返回；需要停止任务时明确调用删除接口或进入受控等待。
- 堆、栈和队列长度按实际数据量估算，并在 `doc/` 记录关键参数。除非确有必要，不引入动态创建和复杂内存池。
- 共享数据必须说明访问上下文；多字段快照使用临界区、队列或复制策略保证一致性。
- 时间戳的记录与比较必须使用同一时钟来源、起始基准和单位。当前电机反馈由 `HAL_GetTick()` 记录毫秒时间，反馈超时也必须使用该时基；任务阶段计时与周期调度使用 FreeRTOS Tick，并通过 `pdMS_TO_TICKS()` 转换毫秒参数。即使两者当前都是 1000 Hz，也禁止直接混用相减。

## CubeMX 生成代码与构建

- 重新生成 CubeMX 代码前，先确认用户代码位于 `USER CODE` 区域，或已迁移到 `bsp/`、`app/` 模块；不要把业务逻辑长期堆在生成文件中。
- 新增 `.c` 文件必须同时更新 `CMakeLists.txt` 或其下游 `cmake/stm32cubemx/CMakeLists.txt` 的源文件和 include 路径。
- 先执行 `cmake --preset Debug`，再执行 `cmake --build --preset Debug`。工具链不可用时，至少进行静态检查并说明未完成构建。
- 不提交 `build/`、编译产物、编辑器缓存和本机路径配置。
- 修改 FreeRTOS、时钟、中断或链接脚本时，必须在 `doc/` 记录原因、影响和验证方式。

## 修改流程（供后续 agent 执行）

1. 阅读本文件、`doc/README.md` 和相关模块文档，确认任务属于 `yuntai/yuntai`。
2. 检查 `git status`，保留用户已有修改，不覆盖未知改动。
3. 先定义模块边界、公开 API、任务/中断上下文和硬件依赖，再实现代码。
4. 以最小改动完成一个可编译的功能；同步更新 `doc/` 中的接口、参数和已知限制。
5. 构建或进行可替代的静态检查，并在交付说明中列出验证命令和未验证部分。

## Bug 修复与防复发规则

每次修复新 Bug，必须把问题所在和防复发方法纳入项目文档：在本文件保留可复用的约束，在 `doc/BUG_FIXES.md` 记录具体案例，在 `doc/CHANGELOG.md` 记录变更。后续 agent 修改相关模块前必须阅读已有案例。

- 记录至少包含：用户看到的现象、问题文件和函数、根因及依据、修复方法、防复发检查、验证结果与未验证项。尚未证实的硬件原因必须注明“待实测”，不能把构建成功写成实机验证成功。
- 修改超时逻辑时，检查时间戳从哪里写入、当前时间从哪里取得、两者单位是否一致，防止再次出现“收到反馈却一直等待”的假离线。
- 电机堵转判断必须区分目标指令与实际反馈，说明反馈单位、有效性、阈值和持续时间；不能仅凭目标值非零、瞬时低速或一次手动扰动判定机械挡块。阈值须可配置，未标定值只能作为调试起点。
- 保护状态必须同时定义进入条件、零输出行为、解除条件和解除后的任务阶段。锁存与自动恢复应符合用户需求；自动恢复必须有明确的反馈条件，不能只按等待时间重新加电。角度移开只是恢复判据，不能声称它已证明机械障碍消失。
- 修改保护阈值或恢复路径时，针对正常启动、短暂手动扰动、持续受阻、反馈超时、解除保护后重新进入测试阶段检查行为；尚未完成的检查写入案例，不省略、不虚报。

## 文档同步要求

新增或改变模块时，至少更新：

- `doc/README.md` 中的模块索引或入口说明；
- 对应模块目录下的 `README.md`（接口、依赖、任务、时序、示例调用）；
- `doc/CHANGELOG.md` 的一条变更记录；
- 如果新增或修改代码风格，更新 `doc/CODING_STYLE.md`；
- 如果需求或硬件信息尚未确定，更新 `doc/OPEN_QUESTIONS.md`，不要自行猜测并固化。
