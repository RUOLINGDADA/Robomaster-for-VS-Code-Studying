# Bug 修复与防复发记录

本文件配合 `AGENTS.md` 使用。后续 agent 修改相关模块前应先阅读对应案例。记录反映代码检查与用户反馈；实机确认尚未完成的部分单独注明，调试阈值不视为最终硬件参数。

## 2026-10-03：双轴硬件测试绑定 Yaw 且反馈快照混用

- **现象**：GM6020 标定和角度环测试只能接入 Yaw；角度测试控制后又重新读取驱动状态，日志可能把不同反馈周期的数据放在一起。
- **根因**：测试接口直接依赖 `YawTask_RuntimeTypeDef`，日志计时使用文件级全局变量，Pitch 没有可复用的正式运行时。
- **修复方法**：新增 `app/gimbal/gimbal_axis` 轴无关运行时；测试参数和日志状态按轴传入；运行时把唯一快照复制到输出结构，测试日志直接引用该快照。Pitch 使用独立 GM6020 ID `0x206`、配置和实例。
- **防复发检查**：测试不能包含第二套 PID/Ramp/保护；每周期只能调用一次快照并贯穿控制、保护、日志；禁止从句柄字段逐项读取反馈。
- **周期输出处理**：保护根据本周期计算出的驱动力请求判断启动和堵转，禁止复用快照中旧输出许可；日志的许可与保护后目标电流来自本周期结果。
- **验证结果与待验证项**：两轴标定、角度环和关闭测试三种编译分支均通过；临时主机程序编译实际驱动/算法/运行时，验证双轴槽位、连续角度、快照竞争与失败、目标越界零输出。双轴电机接线、角度方向、边界和实机恢复仍待台架验证。

## 2026-10-03：固定目标堵转被零命令误解除

- **现象**：固定目标角度测试内部发送零速度命令，堵转保护可能把该零命令误认为操作者松手而重新加电。
- **根因**：通用保护原先允许 `command_direction == 0` 直接进入释放确认，无法区分遥控松手和固定目标测试。
- **修复方法**：固定目标输入由保护层记录为 `fixed_target` 意图；确认堵转后锁存 `stall_requires_manual_release`，必须向堵转反方向移动配置距离（默认约 5 度）且反馈电流下降，再持续确认后恢复；恢复先执行零输出周期。
- **防复发检查**：测试模式不得用定时器或零命令盲目重试；检查位移方向、反馈新鲜度、电流阈值和标定边界。

- **验证结果与待验证项**：临时主机程序验证零命令不解除、同向/不足距离/高电流/边界外不能解除、掉线不清锁、反向移动与连续确认可解除、解除先零输出并可再次触发；真实机械负载仍待实测。

## 2026-10-03：串口 DMA 缓冲区竞争与中文长度回绕

- **现象/风险**：两轴和供弹同时打印时可能覆盖正在 DMA 发送的文本；原 uint8_t 长度让超过 255 字节的中文日志发生回绕，忙等又会拖延控制周期。
- **问题位置**：Core/Src/usart.c 中的格式化发送辅助函数。
- **根因与依据**：共享缓冲区没有覆盖整个格式化/发送寿命的所有权；vsnprintf 返回 int，缩小长度类型丢失高位；串口日志和控制调度不应互相等待。
- **修复方法**：原子取得单个 768 字节 DMA 缓冲区，完成回调释放；增加 usart_try_printf 返回是否接受，保留旧 void 接口；忙或超长立即返回，超长整条拒绝而不截断中文。
- **防复发检查**：重要提示只在成功接受后更新计时，任务后续重试；格式化不能关闭中断或使用 uint8_t 长度，DMA 未完成不能覆盖内存。
- **验证结果与待验证项**：实际 USART 用户代码的主机验证覆盖 DMA 持有期间重入、399 字节长度、超长拒绝、提交失败恢复、ISR 拒绝以及中文提示。编译通过，实板 DMA 中断与串口显示待验证。

## 2026-10-03：角度测试坐标与正式模式不一致

- **现象**：旧测试套件使用首次反馈临时中心和独立测试控制器，测试得到的角度、PID 和范围不能直接代表正式 Yaw 行为。
- **问题位置**：旧 `Core/Inc/test/`、`Core/Src/test/` 测试套件，以及 `task_yaw_runtime.c` 首次反馈临时范围初始化。
- **根因与依据**：测试路径复制了控制器并生成正反向自循环；正式路径使用另一组运行时状态。上电后单圈角度还没有映射到实机标定中心，回绕附近会让固定目标坐标失真。
- **修复方法与行为变化**：删除统一测试目录；新增驱动同级只读标定和固定目标角度硬件测试。GM6020 配置增加首帧角度参考，Yaw/Pitch 测试通过正式运行时执行角度环、速度环、Ramp、限位和堵转保护。未标定时正式路径保持零输出。
- **防复发检查**：硬件调参测试不得复制正式控制算法；标定中心、最小值和最大值必须写入共享配置；关闭测试后应只切换入口，不切换控制参数或坐标系。
- **验证结果与待验证项**：Debug 构建通过；实际中心、左右边界、目标角度恢复、机械限位和堵转阈值仍需急停台架验证。

## 2026-10-03：供弹任务假在线与入口文件过度集中

- **现象**：串口持续出现 `[feed_motor] online=1 phase=wait_feedback`，供弹任务没有进入上弹阶段；同时原任务把配置、阶段状态机、保护、日志和入口全部放在一个文件中。
- **问题位置**：`Core/Src/bsp/c610_m2006/c610_m2006.c` 的 `C610_M2006_Process()`/`C610_M2006_IsOnline()`；旧版 `Core/Src/task/task_feed_motor/task_feed_motor.c`。
- **根因与依据**：初始化时 `last_feedback_tick` 默认为 0，旧在线判断只看状态不是 `OFFLINE`。系统启动前 100 ms 内没有收到反馈时，零时间戳的差值仍可能小于超时，造成假在线；任务入口职责过多也使阶段和安全路径难以独立检查。
- **修复方法与行为变化**：C610 句柄增加 `feedback_received`，只有真实解析过合法反馈且未超时才算在线；超时同时关闭输出。供弹任务拆成 `command/control/protection/runtime` 五个模块，入口只负责初始化和固定周期调度；日志增加 `feedback` 和 `age_ms`，区分“从未收到反馈”和“曾在线后掉线”。
- **防复发检查**：在线判断必须同时检查“收到过有效帧”和“未超过同一时间基准的超时”；不能用零初始化时间戳证明在线。每个任务入口不得重新集中放入命令、控制、保护和日志逻辑；新增宏必须带单位、协议来源和调参风险注释。
- **验证结果与待验证项**：ARM GCC 对新增供弹模块、C610、Yaw、GM6020 和 FreeRTOS 入口执行 `-Wall -Wextra -fsyntax-only` 通过；完整 CMake 构建和真实 CAN 断线/恢复仍待环境和台架验证。

## 2026-10-03：供弹阶段毫秒配置直接当作 Tick 使用

- **现象/风险**：供弹配置字段写明单位为毫秒，但阶段持续时间和日志间隔直接与 FreeRTOS Tick 差值比较；在当前 `configTICK_RATE_HZ=1000` 时不易发现，修改 Tick 频率后会导致测试阶段和日志周期整体变快或变慢。
- **问题位置**：`Core/Src/task/task_feed_motor/task_feed_motor_control.c` 的阶段时长比较；`Core/Src/task/task_feed_motor/task_feed_motor_runtime.c` 的日志限频比较。
- **根因与依据**：`phase_start_tick`、`last_log_tick` 的单位是 Tick，而 `up_time_ms`、`stop_time_ms`、`down_time_ms`、`log_period_ms` 的单位是毫秒；数值相等不代表时间基准相同。
- **修复方法与行为变化**：控制层集中使用 `pdMS_TO_TICKS()` 转换阶段时长，运行时在日志比较前转换日志间隔；阶段计时继续使用无符号 Tick 差值以兼容短间隔回绕。
- **防复发检查**：新增或修改任何任务时间参数时，沿着“字段声明 → 保存单位 → 比较点”检查单位；禁止利用 1 kHz 配置把毫秒宏直接当 Tick。
- **验证结果与待验证项**：已完成代码审计并计划用 ARM GCC 静态检查；不同 Tick 频率下的运行时长和真实串口节流仍需在目标板或主机仿真中验证。

## 2026-10-03：电机型号电流范围混用

> 历史记录说明：本节当时依据示例工程注释得出 GM6020 `±30000`，该结论已被本文件后面的“GM6020 官方手册与旧参考注释冲突”案例纠正；当前代码和规则以官方 Markdown 手册的 GM6020 `±16384` 为准。

- **现象/风险**：GM6020 头文件使用 `[-30000, 30000]`，用户担心这应当是 `[-16384, 16384]`；进一步核对发现 C610/M2006 驱动反而沿用了 C620/3508 的 ±16384 限值。
- **问题位置**：`Core/Inc/bsp/gm6020/gm6020.h` 和 `Core/Inc/bsp/c610_m2006/c610_m2006.h` 的电流范围宏。
- **根因与依据**：参考工程 `参考文档/Robomaster/Code/Development-Board-C-Examples-master/19.gimbal_task/application/CAN_receive.c` 的 `CAN_cmd_gimbal()` 注释明确给出 GM6020 `[-30000,30000]`、M2006 `[-10000,10000]`；同文件 `CAN_cmd_chassis()` 对 C620/3508 给出 `[-16384,16384]`。
- **修复方法与行为变化**：保留 GM6020 ±30000；将 C610/M2006 的驱动层输入钳位改为 ±10000。供弹任务当前 +700/-500 测试电流不变，但以后超范围命令会按 M2006/C610 范围截断。
- **防复发检查**：新增电机驱动或修改电流宏时必须按型号、控制帧槽位和参考资料逐项核对；不能依据 `int16_t` 类型、其它电机或反馈字段范围推导控制上限。
- **验证结果与待验证项**：已完成参考源码静态核对，并将当前宏、驱动钳位和模块文档同步；实际电调固件是否采用相同输入边界、长期安全电流和温升仍需台架验证。

- **防复发检查**：不能按 C620、GM6020 或示例代码的反馈布局推断 C610 字段；每种电机必须逐字节核对官方手册。没有明确温度字段时，禁止把保留字节接入温度保护或日志标签。
- **验证结果与待验证项**：已完成 C610 驱动、供弹日志和模块文档同步，并完成 ARM GCC 语法检查；C610 实际固件错误码和长期保护策略仍需台架验证。

## 2026-10-03：GM6020 官方手册与旧参考注释冲突

- **现象**：旧规则和 GM6020 头文件把电流原始范围写成 `[-30000, 30000]`，发送函数还使用 `0x1FF`；重新阅读 `参考文档/markdown/RoboMaster_GM6020----------20231013.md` 后发现这两个结论都不适用于 GM6020 电流控制。
- **问题位置**：`Core/Inc/bsp/gm6020/gm6020.h` 的电流范围、反馈 ID 和控制 ID 宏；`Core/Src/bsp/gm6020/gm6020.c` 的 `Gm6020_Send()`；`doc/modules/gm6020/README.md` 与 `AGENTS.md` 的协议说明。
- **根因与依据**：官方手册明确写出电流给定范围为 `-16384~0~16384`，电流控制标识符为 `0x1FE`（ID 1~4）和 `0x2FE`（ID 5~7）；`0x1FF/0x2FF` 是电压控制标识符。旧的 `±30000` 来自示例工程注释，优先级低于当前核对的官方 Markdown 手册。
- **修复方法与行为变化**：将 GM6020 电流钳位改为 `[-16384, 16384]`；发送改为按 ID 1~4、5~7 分别聚合到 `0x1FE/0x2FE`；反馈接收范围扩展为 `0x205~0x20B`，但本工程仍默认只注册 Yaw/Pitch 两个句柄；补充电压控制宏并明确本驱动不发送。
- **防复发检查**：核对电机协议时必须优先查看 `参考文档/markdown` 的对应型号手册，并同时核对“控制模式、控制帧 ID、反馈 ID、DLC、字段范围”五项；示例代码注释只能作为交叉参考，不能覆盖官方手册。多电机聚合发送必须验证每个 ID 组的槽位不会越过 8 字节数组。
- **验证结果与待验证项**：已完成源代码、规则和 GM6020/C610 模块文档同步；已检查 C610/M2006 的 `±10000`、`0x200/0x1FF`、`0x201~0x208` 与官方手册一致。仍需在已打开 GM6020 电流环的实际固件上确认 `0x1FE` 控制生效；当前环境的完整 CMake 构建和 CAN 台架验证未完成。

## 2026-10-03：Yaw 工程化重构中的换向和反馈恢复风险

> 历史记录：当前反馈恢复只清候选计时并重置控制历史，保留已确认的堵转；固定目标解除采用上文手动移开规则。

- **现象/风险**：旧 Yaw 是固定正负电流测试，保护逻辑与任务阶段耦合；换向时电流 Ramp 仍可能保持旧方向，若只看当前电流方向和低速，可能跨过换向窗口累计堵转。CAN 反馈掉线后恢复时，控制器还可能保留掉线前的目标角度。
- **问题位置**：旧版 task_yaw_protection.c 的候选计时和旧版 task_yaw_runtime.c 的反馈恢复路径；当前实现位于 Core/Src/app/gimbal/gimbal_protection.c 与 gimbal_axis.c。
- **根因与依据**：命令方向、实际输出方向和反馈状态是不同时间点的数据；电流变化率限制会让它们暂时不一致。掉线期间机构可能被人手移动，旧目标角度不再是安全保持点。
- **修复方法与行为变化**：保护层记录命令方向，命令换向时重新启动换向宽限，并要求命令方向与当前请求电流同向才形成堵转证据。反馈从 `FEEDBACK_LOST` 恢复时，控制器以当前连续角度重置、保护状态清零、先发送一个完整周期零电流，再接受新命令。
- **防复发检查**：修改 Ramp、命令输入或掉线处理时，必须分别追踪命令符号、控制输出符号、反馈方向和任务阶段；验证换向、松手、掉线恢复不会跨用旧目标。任何自动恢复必须有实际反馈条件，不能按固定延时盲目重新加电。
- **验证结果与待验证项**：ARM GCC `-fsyntax-only -Wall` 通过；尚未完成主机时序仿真和真实机械台架验证，换向宽限、PID 参数、堵转阈值和 180°边界仍需实测。

## 2026-10-02：电机收到反馈却一直等待

- **现象**：用户已收到 Yaw `0x205` 反馈，日志却显示 `online=1 phase=wait_feedback state=disabled output=0`。
- **问题位置**：当时的单文件 Yaw 入口（现已迁移为 `Core/Src/task/task_yaw/task_yaw.c`）向 `Gm6020_Process()` 传入 FreeRTOS Tick；GM6020 接收函数却使用 `HAL_GetTick()` 保存 `last_feedback_tick`。
- **根因与依据**：记录与比较使用不同时间基准。HAL 毫秒计数和 FreeRTOS Tick 即使频率相同，启动时刻也可能不同；相减会误判超时。任务关闭输出与接收中断更新在线状态还会交错，使日志表面上显示在线。
- **修复**：当前 Yaw 反馈超时统一传入 `HAL_GetTick()`；阶段计时、日志限频和 `vTaskDelayUntil()` 仍使用 FreeRTOS Tick。
- **防复发检查**：从时间戳写入处追踪到每个比较处，核对时钟来源、单位和起始基准；接口注释必须写清要求。不能只因为当前 1 Tick 等于 1 ms 就认为可以混用。
- **验证范围**：修复后 Debug 构建通过；用户后续日志出现 Yaw `phase=protected`，表明任务已离开最初的等待路径。长时间运行、反馈断开/恢复和计数回绕仍需实测或针对性模拟。

## 2026-10-02：Yaw 堵转误判与保护不能恢复

> 历史记录：下列阈值与状态属于当时版本；当前使用各轴配置、通用保护层和本文件前述固定目标恢复条件，勿按旧值重新实现。

- **现象**：用户报告轻微手动移动后进入 `phase=protected state=blocked limit=physical_blocked`，随后一直保持零输出，不能继续自循环。
- **问题位置**：`Core/Src/bsp/gm6020/gm6020.c` 的 `Gm6020_Process()`；当时的单文件 Yaw 实现（当前控制与保护已迁移至 app/gimbal）中的保护参数和恢复分支。
- **根因与依据**：早期实现只检查目标电流和低速，目标值不能证明实际电流已经建立；随后增加反馈电流检查，但 Yaw 的 400 原始值阈值仍被用户反馈为过于敏感。另外原实现锁存 `BLOCKED` 后直接返回，既没有解除条件，也没有让任务离开 `PROTECTED` 的路径。锁存是原设计选择，但与用户需要继续测试的要求不一致。
- **当前修复**：目标电流非零、反馈电流绝对值达到阈值且速度接近零，持续指定时间才触发。Yaw 调试阈值从 400 调整为 1000 原始值，低速阈值为 5 rpm，持续时间为 200 ms。记录堵转位置；输出关闭、反馈有效、反馈电流低于阈值且连续角度离开该位置至少 32 个编码器计数（约 1.4°）时解除 `BLOCKED`。任务从 `PROTECTED` 回到 `WAIT_FEEDBACK`，下一轮再使能自循环。
- **恢复边界**：这里只自动解除物理堵转 `BLOCKED`；软件角度上下限 `LIMIT_MIN/MAX` 仍保留锁存规则。角度变化是恢复启发式，不能证明障碍已消失；代码不按固定等待时间盲目重试。
- **防复发检查**：保护参数必须结合实际负载标定，不能把本次 1000/200 ms/32 计数复制成所有电机的固定标准。进入保护和解除保护须同时检查驱动状态与任务阶段，避免只清驱动标志而任务仍停在 `PROTECTED`。
- **验证范围**：代码修改后 Debug 构建通过。新阈值能否避免手动扰动误判、持续受阻能否及时停机、反馈断开时能否保持停止、手动移开后能否按要求恢复，均待实机确认。

## 2026-10-02：CubeMX 中缺少 Pitch 任务

- **现象**：用户打开 CubeMX 后看不到 `task_pitch`，即使手动补写的 C 代码能够编译。
- **问题位置**：`yuntai.ioc` 的 `FREERTOS.IPParameters` 与任务配置字段。
- **根因与依据**：误把多个任务拆成 `Tasks01/Tasks02/Tasks03`。本仓库已有多任务 CubeMX 示例采用单个 `FREERTOS.Tasks01`，任务记录之间以分号分隔。
- **修复**：三个任务合并到同一个 `FREERTOS.Tasks01`，移除多余字段；同步补齐 Pitch 弱入口、声明和创建代码。
- **防复发检查**：修改 `.ioc` 前参考已有的 CubeMX 格式；既检查配置源，也检查生成结果。C 构建成功不能证明 CubeMX 已识别任务配置。
- **验证范围**：字段已按仓库示例修正，C 代码构建通过；修正后 CubeMX 界面是否显示全部任务仍需重新加载工程确认。
