# yuntai 项目规则

## 适用范围

本文件适用于当前目录及其所有子目录。修改本工程前，先阅读本文件和 `doc/README.md`；再根据任务阅读 `doc/` 下的相关专题文档。父目录中的其它示例工程不属于本项目修改范围。

## 项目目标与技术基线

- 目标平台：STM32F407，HAL，C11，CMake，arm-none-eabi-gcc。
- 系统基础：FreeRTOS。任务、队列、信号量、软件定时器和事件组按实际功能添加，不为了形式完整而增加对象。
- 当前工程入口：`Core/Src/main.c`、`Core/Src/freertos.c`、`CMakeLists.txt` 和 `cmake/stm32cubemx/`。
- 参考风格：`../can_example`。优先保持其命名、目录、头文件保护、注释语言和模块拆分方式；不复制与当前功能无关的复杂错误回调体系。

## 目录与模块边界

采用多文件夹、多层级的模块化结构。一个较大的设备驱动对应一个目录；小功能也可以按功能单独成目录。

```text
Core/
  Inc/                         # 公共头文件、CubeMX 生成头文件
    bsp/<driver>/              # 设备驱动头文件
    app/<feature>/              # 应用功能头文件
  Src/
    bsp/<driver>/              # 设备驱动源文件
    app/<feature>/              # FreeRTOS 任务或应用逻辑
doc/                           # 工程对接、协议、决策和变更记录
```

- 驱动目录按设备或外设命名，例如 `bsp/c620/`、`bsp/imu/`、`bsp/uart/`。
- 应用目录按功能命名，例如 `app/gimbal/`、`app/remote/`、`app/chassis/`。
- 一个模块公开一个主头文件，内部辅助函数和状态尽量保留在 `.c` 文件中。
- 模块之间通过公开 API、数据结构和 FreeRTOS IPC 通信，不直接访问其它模块的 `static` 数据。
- 不因为目录规则机械拆分只有几行且不会复用的代码；拆分应降低依赖和便于替换。

### 当前任务目录约束

- 每个 FreeRTOS 任务使用独立目录：`Core/Inc/task/<task_name>/` 与 `Core/Src/task/<task_name>/`；入口只负责初始化与周期调度，配置和命令适配按需保存。多轴可复用的控制、保护和运行时放在 `app/gimbal/`，不要为了目录形式在任务下复制一套实现。
- 供弹任务也必须遵守同样的拆分：`task_feed_motor.c` 只调度，`config/command/control/runtime` 分别保存参数、命令快照、阶段状态机和硬件组合。
- `freertos.c` 只保留 CubeMX 创建、属性和 `__weak` 安全兜底；业务强入口放在任务目录，并在顶层 CMake 中显式列出。
- 供弹阶段时长、日志间隔等配置统一以毫秒保存；与 `TickType_t` 比较前必须在使用点调用 `pdMS_TO_TICKS()`，禁止利用当前 1 kHz 配置直接把毫秒数当 Tick 数。
- `task_yaw` 只控制水平 Yaw 轴；`task_pitch` 只控制纵向 Pitch 轴；两个 GM6020 必须使用独立句柄。供弹电机只有一个，目录迁移不能复制出第二个实例。
- Yaw 正式流程是相对速度命令、目标角度保持、角度 P/速度 PI、电流 Ramp 和软件边界过滤；固定左右电流自循环只能作为单独测试模式，不能混入正式任务入口。
- GM6020 通用驱动不判断动态物理堵转，也不锁存软件限位；Yaw/Pitch 由同一个 `GimbalAxis` 运行时过滤继续向外的命令并保持闭环。反馈新鲜度、参数合法性和协议电流范围仍由基础驱动/运行时检查。
- `Gm6020_GetSnapshot()` 是任务与硬件测试读取反馈、状态的强制入口；禁止任务直接拼接 CAN ISR 可能正在更新的多个句柄字段。

### 任务配置归属

- 上板调节的行为参数集中在对应 `Core/Inc/task/task_*/*_config.h`：输入映射、鼠标灵敏度与时序、PID、Ramp、标定、测试时序和电流、任务遥测周期。
- 任务从配置宏组装结构体，再传给 BSP、算法或通用运行时。BSP 和算法保持单向依赖，不包含任务配置头。
- BSP 保留协议字段、帧长、ID 公式、硬件协议边界及必要安全默认值。算法通过配置结构接收产品参数。CubeMX/FreeRTOS 参数由 `.ioc` 管理。
- 配置只有一个默认来源。保留现有 `#ifndef` 覆盖机制；迁移后删除旧宏和兼容别名，同步消费点、模块文档和静态检查。
- 任务配置仅保留简短使用说明。文件头说明何种现象需要调整哪组参数；宏行说明单位、范围和直接副作用。复杂解释集中在模块 README。
- 整理参数时保留已有实测数值。只有用户明确授权的参数可以改变。

### 硬件测试与调参规则

- 永久保留的测试代码必须与被测驱动同级：GM6020 放在 `Core/Inc/bsp/gm6020/`、`Core/Src/bsp/gm6020/`，C610/M2006 放在对应驱动目录；禁止重新建立统一 `Core/Inc/test/`、`Core/Src/test/` 测试目录。
- 只提交真正需要烧录上板的硬件测试，例如 GM6020 角度标定、固定目标角度保持和 C610 只读手动角度步长测量；反馈解析、PID、Ramp、回绕、钳位等纯逻辑由 agent 使用临时脚本或临时主机程序验证，验证后不提交。
- 测试文件使用 `test_<driver>_<feature>.h/.c` 命名。每个测试头文件必须说明硬件需求、初始化顺序、参数单位、调用上下文、输出行为和安全限制。
- 硬件测试必须直接复用正式驱动和正式算法，不得复制另一套 CAN 解析、PID、Ramp、限位或堵转保护；调参结果必须能够直接写入正式配置。
- 硬件测试函数必须是非阻塞单步函数，每次任务调用只推进一个周期；不能调用 `HAL_Delay`，不能在 CAN ISR 中打印、等待或调用普通 FreeRTOS API。
- 每个电机任务最多保留一个简单的硬件测试模式分支；同一周期只能由测试路径或正式路径其中一个写入电流，不能使用测试套件同时分发多个会写电流的测试。
- Yaw/Pitch 测试分为“只读手动标定”和“固定目标角度闭环”两种模式。标定模式强制零电流；角度环模式使用已记录的中心、最小和最大连续角度，目标角度以中心为参考，用户只修改带单位注释的配置宏。
- 标定数据必须记录来源和实测状态。未完成标定时正式控制保持零输出，不能回退到未经确认的临时范围继续驱动。
- GM6020 角度环硬件测试必须输出目标角度、实际连续角度、误差、目标速度、实际速度、目标电流、反馈电流、输出许可、限位和保护原因；日志只能在任务上下文使用中文输出。
- GM6020 标定和固定目标测试必须使用轴无关接口，参数通过 `Gm6020_CalibrationTypeDef` 和各轴独立配置传入；Yaw/Pitch 不得复制测试算法或共享测试状态。
- 测试和通用轴运行时每个控制周期只取得一份 `Gm6020_GetSnapshot()` 快照，控制、保护和日志必须引用同一份快照；不得在日志中混读句柄字段或重新取下一帧拼接数据。
- 标定日志必须说明零电流状态，并提示中位、左/右或下/上物理边界的记录操作；最小/最大值最终按实测连续计数排序；程序不自动假定用户已经完成任何一步。
- 固定目标测试使用正式轴闭环；零速度只表示固定目标保持，不应被边界过滤成遥控器回中。
- USART DMA 日志发送必须非阻塞，使用原子操作取得缓冲区所有权，DMA 完成回调后才释放；不能覆盖缓冲区、忙等或因日志繁忙触发 Error_Handler。格式化长度使用 `int`，超长文本整条拒绝以免截断中文；重要提示使用可返回接受结果的接口重试。
- 所有串口打印使用 `app/log/log.h` 的 `LOG_TRY_PRINTF(category, ...)`，直接进入唯一 `Log_TryPrintf()` 后端。开关集中在 `log_config.h`；Yaw、Pitch 和供弹各自控制正式及测试日志。共用测试由所属任务传入分类，共用文本只共享格式和快照参数，不增加日志转发函数。关闭分类时格式参数不求值，控制和安全操作在日志调用外执行。
- 连续角度等 `int64_t` 日志先转为十进制字符串，再用 `%s` 输出；目标端未验证长长整型格式时，不直接使用 `%lld`。修改转换时覆盖零、正负数和 INT64_MIN/MAX；格式化失败不能改变控制状态。

- 固定目标越界配置直接判无效并零输出；反馈掉线立即发零，恢复后只清 PID、滤波和 Ramp 历史，保留最后目标位置。
- 电流聚合帧的“读取全部电机槽位 → 构建 → 提交 HAL 邮箱”必须在同一个短临界区完成，防止任务切换提交旧帧；临界区内禁止等待或打印。软件限位只过滤继续向外的目标积分和速度前馈；回中或命令超时保持最后目标，反向命令同周期积分。越界反馈仍按正常闭环计算，不自动重定位目标；反馈掉线发零。
- 日志明确区分“控制器计算电流”“输出许可”和“CAN 已提交”；HAL 接受不等于电调实际执行。所有反馈字段必须有快照有效性和反馈年龄。
- 首帧标定参考要求启动位置相对中心位于可唯一解释的半圈内；禁止误写为“机械总行程必须小于半圈”。时间戳 0 ms 可能是真实反馈，不得单靠零时间戳判定离线。

### 宏定义注释规则

- 每个自建或本次新增 `#define` 都必须在同一行或紧邻上一行写明用途、单位、协议来源或边界；时间宏必须写 `ms`/`Tick`，电流宏必须写原始值，CAN ID 宏必须写标准帧含义。
- 任务配置注释面向使用者。每组只写适用现象，每个宏用短句说明单位、有效范围和直接副作用。控制原理、公式和协议引用放模块 README。
- 调整级联 PID 前必须核对误差单位及各级限幅，算出进入饱和的误差阈值；不能在速度/电流已饱和时继续堆位置增益。每轮尽量只改一组参数；日志未区分 PI 原始输出与 Ramp 后输出时，不得仅凭反向电流断言积分失控或方向反接，参数稳定性须标注待实测。
- 不同电机型号的电流原始值范围必须分开核对：GM6020 电流控制按官方手册使用 `[-16384, 16384]`，C620/3508 使用 `[-16384, 16384]`，M2006/C610 使用 `[-10000, 10000]`；禁止按“都是 int16_t”复用限值。GM6020 还必须区分电流控制帧 `0x1FE/0x2FE` 与电压控制帧 `0x1FF/0x2FF`。
- 头文件保护宏也要说明“防止重复包含”；不要留下只有名字、没有解释的项目宏。
- CubeMX/HAL/FreeRTOS 自动生成宏保留官方注释；如果 agent 修改其数值，必须补充修改原因和影响到 `doc/CHANGELOG.md`。
- CAN 反馈字段也必须按具体型号手册逐字节核对；不能因为多个 RoboMaster 电机都使用 8 字节帧，就把 `DATA[6]` 一律当温度或把 `DATA[7]` 一律当错误码。保留字节只能原样记录，不能参与保护判断。

## 命名与代码风格

- 文件名、目录名使用小写英文和下划线；类型使用 `PascalCaseTypeDef`；函数使用 `Module_Action`；宏使用 `MODULE_NAME`；枚举值使用 `MODULE_STATE_xxx`；静态文件级对象使用 `g_` 前缀。
- 头文件使用 `#ifndef`/`#define`/`#endif` 保护；公共接口放头文件，私有实现放源文件。
- 缩进和大括号参照 `can_example`，使用 2 个空格缩进，函数和结构体字段按功能分组。
- 注释要让没有 STM32 经验的读者能够理解硬件发生了什么、代码为什么这样写、改动会影响什么。必须说明意图、协议来源、单位、时序、内存/中断上下文和边界条件。
- 自建代码注释使用中文，采用 ASD STE100 的短句、主动语态、术语一致和单一意图原则。STE100 正式规范适用于受控英语；本工程采用中文受控写法，不声明严格符合受控英语标准。关键注释保留必要的接口前提、单位和失败行为。
- 保留准确的技术注释，修改实现时同步修正对应说明。源码注释只描述当前职责、单位、范围、时序和必要依据；日期、变更经过、旧新参数对比、用户对话和验收记录放入 `doc/`，不写入源码注释。官方版权与 CubeMX 标记保持完整。
- 注释优先解释坐标系选择、数据一致性、时序、资源所有权和安全边界的设计取舍，不要只把表达式逐字翻译成“设置/判断/累加”；如果某个前提不成立会导致误判、越界、旧命令继续执行或无法恢复，也要写出后果。
- 注释采用多种层次：文件头多行注释说明模块职责；函数多行注释说明参数、返回值和调用上下文；代码块多行注释解释状态机、协议帧、资源清理等整体思路；关键行使用单行注释标出寄存器位、字节序、单位换算和容易踩坑的地方。
- 注释不要求机械解释每一行，但凡涉及底层行为或容易被小白误改的代码，都要解释原因。例如 `volatile` 的可见性边界、`FromISR` API、DMA 缓冲区、结构体对齐、大小端、整数溢出、Tick 溢出、临界区和清零时机。
- 变量名体现单位或范围，例如 `timeout_ms`、`angle_deg`、`current_raw`；避免没有上下文的 `temp`、`data1`、`flag2`。
- 优先使用明确的返回值和简单控制流。功能已经明确且能保证资源释放时，可以使用 `goto` 统一失败清理；不要为了“结构化”引入多余层级。
- 中断回调只做必要的硬件/事件记录；耗时工作、日志和业务处理放到 FreeRTOS 任务或主循环。
- 只保留与功能有关的回调。不要为每一种理论错误创建空回调；错误处理采用返回值、状态字段或单个必要的故障通知即可。

### 注释最低要求

- 每个自建 `.c`/`.h` 文件有文件级多行说明，写明模块作用、硬件接口或协议范围、运行上下文和不负责的内容。
- 每个公开函数有多行说明，至少包含 `@brief`、参数、返回值；涉及单位、任务/ISR 限制、线程安全和失败后状态时必须明确写出。
- 每个自有 `.c` 中未在头文件声明的函数（包括 `static` 辅助函数）都必须在函数前有紧邻的用途说明；简单转换、限幅、查找函数写 1~2 行即可，复杂算法、状态机、保护、并发或特殊前提再补充输入条件、处理顺序、失败出口和设计理由。HAL/CubeMX 官方生成函数不因本规则改写版权或模板注释。
- 每个复杂函数至少有一段“先做什么、为什么这样做、失败如何退出”的块注释；资源释放和统一失败出口可以使用 `goto`，并在出口前说明清理顺序。
- 单行注释放在具体语句后或语句前，只解释该行的底层坑点，不重复函数名。例如 `/* CAN 反馈为大端，STM32 内存本身按小端解释，不能直接 memcpy 到 int16_t。 */`。
- 对限位、堵转、滤波、Ramp、PID、快照和 DMA 等关键路径，至少说明一个可验证的错误后果；例如“单圈回绕会让大小关系失效”“DMA 完成前覆盖缓冲区会发送被改写的内容”。
- 注释中的数值要带单位或协议含义；不要只写“延时”“限制”“状态”。
- 驱动公开和内部结构体的每个成员都必须有就地注释，至少说明单位、协议字节、有效范围、初始化状态或 ISR/任务访问上下文；不能只给结构体整体写说明而让成员靠猜。
- 协议来源和必要硬件前提可在注释中简述；完整资料出处、实测过程及验收状态记录在模块文档，不确定内容写入 `doc/OPEN_QUESTIONS.md`。

## FreeRTOS 使用规则

- 每个任务有明确职责、周期/阻塞条件、栈大小和优先级依据。周期任务使用 `vTaskDelayUntil` 或等价的 CMSIS-RTOS 接口保持周期。
- 任务间优先使用队列、通知、事件组或信号量传递事件；避免用大量全局 `volatile` 标志拼接协议。
- ISR 中只能调用带 `FromISR` 后缀的 API，并正确处理 `higher_priority_task_woken`。
- 任务入口不得返回；需要停止任务时明确调用删除接口或进入受控等待。
- 堆、栈和队列长度按实际数据量估算，并在 `doc/` 记录关键参数。除非确有必要，不引入动态创建和复杂内存池。
- 共享数据必须说明访问上下文；多字段快照使用临界区、队列或复制策略保证一致性。
- 时间戳的记录与比较必须使用同一时钟来源、起始基准和单位。当前电机反馈由 `HAL_GetTick()` 记录毫秒时间，反馈超时也必须使用该时基；任务阶段计时与周期调度使用 FreeRTOS Tick，并通过 `pdMS_TO_TICKS()` 转换毫秒参数。即使两者当前都是 1000 Hz，也禁止直接混用相减。

## CubeMX 生成代码与构建

- CubeMX 生成文件中的所有用户修改必须放在对应的 `/* USER CODE BEGIN ... */` 与 `/* USER CODE END ... */` 注释对之间；生成区只能保留 CubeMX 自动生成内容。重新生成会覆盖生成区，不能把生成区中的修改当作持久代码。
- 适用文件包括 `Core/Src/*.c`、`Core/Inc/*.h`、`*.ioc` 以及 CubeMX 管理的 `cmake/stm32cubemx/` 文件。新增 include、类型、全局变量、宏、函数声明、初始化补丁、中断补丁和回调逻辑，必须放入该文件已有的 `USER CODE` 区域；如果文件没有合适区域，先新增成对的 `USER CODE BEGIN/END` 标记，并保持 CubeMX 可识别的格式。
- 业务实现、驱动和任务逻辑优先放在非生成的 `Core/Inc/bsp/`、`Core/Src/bsp/`、`Core/Inc/app/`、`Core/Src/app/` 或 `Core/Inc/task/`、`Core/Src/task/` 文件中，再从生成文件的 `USER CODE` 区域调用；不要为了绕过区域限制把大段业务代码塞进 `main.c`、`freertos.c`、`stm32f4xx_it.c` 或外设初始化函数。
- 修改 CubeMX 初始化参数时，优先修改 `.ioc` 后重新生成；需要保留的运行时补丁必须写在 `USER CODE BEGIN <外设>_Init 0/1/2`、`USER CODE BEGIN <外设>_MspInit 0/1`、中断处理器的 `USER CODE` 区域或独立模块中。禁止只改生成后的 HAL 初始化字段而不更新 `.ioc`。
- 每次重新生成后必须检查 `git diff`，确认 `USER CODE` 区域和独立模块仍然存在；若生成结果删除了用户逻辑，先恢复/迁移后再继续修改。交付前说明哪些改动由 `.ioc` 持久化、哪些改动由 `USER CODE` 区域持久化、哪些改动位于独立非生成模块。
- 新增 `.c` 文件必须同时更新 `CMakeLists.txt` 或其下游 `cmake/stm32cubemx/CMakeLists.txt` 的源文件和 include 路径。
- 默认直接修改当前工程源码，由用户在 VS Code 中构建并烧录最新代码。agent 使用差异、引用及静态检查验证；需要时运行临时主机逻辑验证。只有用户明确要求构建或固件交付时，才执行固件编译、链接或生成 ELF/BIN/HEX，也不自行创建诊断固件或独立构建目录。
- 不提交 `build/`、编译产物、编辑器缓存和本机路径配置。
- 清理旧文件前核对 CMake、include、调用点及文档引用；保留仍在使用的硬件测试和 VS Code 构建配置，清除废弃验证产物并同步入口说明。
- 修改 FreeRTOS、时钟、中断或链接脚本时，必须在 `doc/` 记录原因、影响和验证方式。

## 技能使用

- 根据任务选择可用技能，先读对应 `SKILL.md`。架构边界使用 `codebase-design`，项目规则修改使用 `writing-for-agents`；用户要求 grill me 时使用 `grilling`。
- 技能用于解决当前问题。已确认的设计决定直接执行，避免重复询问。技能的外部写入、安装和显式调用限制继续遵守工作区入口规则。

## 修改流程（供后续 agent 执行）

1. 阅读本文件、`doc/README.md` 和相关模块文档，确认任务属于 `yuntai/yuntai`。
2. 检查 `git status`，保留用户已有修改，不覆盖未知改动。
3. 先定义模块边界、公开 API、任务/中断上下文和硬件依赖，再实现代码。
4. 以最小改动完成一个可编译的功能；同步更新 `doc/` 中的接口、参数和已知限制。
5. 完成静态检查及必要的临时主机验证，在交付说明中写明验证范围；固件构建遵守上面的用户授权规则。

## Bug 修复与防复发规则

每次修复新 Bug，必须把问题所在和防复发方法纳入项目文档：在本文件保留可复用的约束，在 `doc/BUG_FIXES.md` 记录具体案例，在 `doc/CHANGELOG.md` 记录变更。后续 agent 修改相关模块前必须阅读已有案例。

- 记录至少包含：用户看到的现象、问题文件和函数、根因及依据、修复方法、防复发检查、验证结果与未验证项。尚未证实的硬件原因必须注明“待实测”，不能把构建成功写成实机验证成功。
- 修改INS安装矩阵时，先把实际动作和日志时间ms对应，联合核对静止比力与动态陀螺原码；区分计算链正确与物理轴向正确。比力/角速度共用一次正交右手变换，三轴伴随变化和未验收项见INS模块；测试先等READY，磁矩阵独立验证。
- 接入或修改云台惯性反馈时，用固定底座下同次动作的编码器与惯性角增量确认每轴映射；物理右转/抬头为正不代表编码器正向。角度和欧拉角速度必须同符号映射，独立保留电流与编码器测速符号；用实测窗口验证零输入目标冻结且电流反向纠偏，案例见`doc/modules/ins/yaw_runaway_20261019.md`。
- 修改BMI变换后，复核历史磁轴结论依赖的坐标和跨传感器相对映射；保留同一相对安装假设时计算R_MAG_new=R_BMI_new*transpose(R_BMI_old)*R_MAG_old，再用独立磁观测验收。物理安装变化或旧假设未证实须重新辨识；同PCB不是同轴依据，案例见doc/BUG_FIXES.md的107秒记录。
- 修改超时逻辑时，检查时间戳从哪里写入、当前时间从哪里取得、两者单位是否一致，防止再次出现“收到反馈却一直等待”的假离线。
- 修改上位机串口帧时，用实际接收端解析器验证发送原文、分段接收与终止符；以接收回调或数据缓冲更新作为通过条件。MotionCal案例见 `doc/BUG_FIXES.md` 的2026-10-18记录。
- 切换 CAN 实例时，同步核对任务句柄、聚合发送、IRQ、共享过滤器分界和 CAN1 从属时钟；过滤器 bank 必须属于目标总线。复现与检查步骤见 `doc/BUG_FIXES.md` 的 2026-10-16 案例。
- 修改 DBUS 鼠标适配时先阅读 `doc/modules/mouse_virtual_joystick/README.md`；相对位移按合法帧序号只消费一次，合法帧批次保留位移代数和，使用对应接收时间差测速并替换速度。新零帧清本轴，X/Y 独立配置浮点增益和缺帧保持/回中；内部及发布速度保留小数。回归覆盖等速不累加、反向立即变号、零帧清零、跨帧间隔/批量归一化、首帧/同毫秒、NaN/Inf/溢出、重复帧、离线及时间/序号回绕；命令保留真实接收时间戳，案例见输入模块报告。
- 状态机在同一周期改变目标后，输出前重新计算误差和依赖目标的局部量；验证阶段切换的首个输出周期，避免下一发沿用旧误差。
- GM6020 云台路径不实现动态堵转判断或锁存；供弹使用连续角度固定步长。鼠标左键按下沿建立一个步长，目标完成后短按停止、长按建立下一步；键盘 Shift 独立控制 C615 活动 PWM。修改时回归短按一步、长按连续步长、释放后的目标完成、Shift 启停、命令/反馈安全门和连续角度回绕。机械方向、每发 count 和温升仍须台架确认。
- 供弹按下沿以当前 FreeRTOS Tick 建立长按起点，不能计入按下前的周期；每步到位周期必须输出零并从到位时刻计步间停顿，长按也不能同周期重建目标。步长符号必须参与逻辑电流方向，目标加法先检查 int64_t 边界。Shift 松开同周期调用停止 PWM，命令失效同时清除左键和 Shift。回归方法见 `doc/BUG_FIXES.md` 的 2026-10-11 案例。
- 修改软件边界或反馈恢复路径时，检查正常启动、边界外向输入、零输入目标冻结、反向同周期积分、越界反馈闭环、反馈超时清零和恢复后最后目标不变；人工边界须按同一连续计数参考下的实测挡块留出余量，挡块处显示“边界无”先核对标定，不先裁剪自稳输出。未完成项写入案例，见`doc/modules/gimbal/pitch_stop_mouse_speed_20261019.md`。
- 修改位置积分抗饱和时，保存上一周期积分并在拒绝候选积分时恢复；用大正/负误差验证积分始终位于配置上限内，不能从已钳位积分减去未钳位增量。

## 文档同步要求

新增或改变模块时，至少更新：

- `doc/README.md` 中的模块索引或入口说明；
- 对应模块目录下的 `README.md`（接口、依赖、任务、时序、示例调用）；
- `doc/CHANGELOG.md` 的一条变更记录；
- 如果新增或修改代码风格，更新 `doc/CODING_STYLE.md`；
- 如果需求或硬件信息尚未确定，更新 `doc/OPEN_QUESTIONS.md`，不要自行猜测并固化。

### 功能完成的文档门槛

- 功能只有在代码验证和文档同步都完成后才算交付：必须检查 `doc/TECHNICAL_ARCHITECTURE.md` 的受影响章节、对应模块 `README.md` 和 `doc/CHANGELOG.md`。
- 新增或修改每个宏时，必须记录单位、有效范围、它改变的公式/状态/安全门和直接副作用；不能只记录宏名称和值。
- 新增或修改 `Core` 中的宏或关键实现函数后，必须运行 `powershell -NoProfile -File doc/tools/update_technical_reference.ps1` 重建 `doc/MACRO_REFERENCE.md` 和 `doc/IMPLEMENTATION_GUIDE.md`，再人工检查条件分支、正式函数定义、单位和算法解释；生成附录不得只靠自动输出交付。
- 新增或修改接口、任务、协议或并发路径时，必须记录调用上下文、数据所有权、时间基准、失败行为和硬件假设。
- 需求、机械参数、方向或实测结果未确认时，必须同步写入 `doc/OPEN_QUESTIONS.md` 并标记“待实测/待确认”；构建通过不能替代上板验证。
- 完成功能后运行 `git diff --check -- .` 并核对引用和文档；默认不生成固件，交付说明准确区分静态检查、主机验证与用户上板验证。
