# Bug 修复与防复发记录

本文件配合 `AGENTS.md` 使用。后续 agent 修改相关模块前应先阅读对应案例。记录反映代码检查与用户反馈；实机确认尚未完成的部分单独注明，调试阈值不视为最终硬件参数。

## 2026-10-05：Pitch 到达最大限位突然变为零电流（保护层清理）

- **现象**：Pitch 到达或略微超过软件最大限位后，控制电流突然变为零；回中时不能稳定保持，反向操作也可能被旧状态拦截。
- **根因**：旧版控制器、动态堵转锁存、GM6020 驱动方向拦截和固定限位电流共同覆盖了正常闭环结果；任一层进入保护状态都会把最终输出改成零。供弹任务也存在独立保护模块，形成重复安全路径。
- **修复方法**：删除 `gimbal_protection.*` 和 `task_feed_motor_protection.*`。GM6020 限位只报告当前几何边界；`GimbalControl_Update()` 在边界过滤继续向外的命令，把目标重定位到当前反馈位置，继续运行角度环、速度环、Ramp 和抗重力补偿；反向命令同周期生效。命令失效/超时按零速度保持，反馈超时、快照无效、标定或参数无效仍发送零电流。
- **防复发检查**：边界外向输入不能继续积分目标；回中和超时不能清除闭环历史；反向输入必须在同周期产生正常闭环请求；固定目标越界必须零输出；GM6020 `SetCurrent()` 不能按边界拒绝上层电流；C610 反馈掉线必须清零。
- **验证结果与待验证项**：GM6020、云台控制/运行时、Yaw/Pitch、供弹和测试源已通过 ARM GCC `-std=c11 -Wall -Wextra -Werror -fsyntax-only`；当前环境没有 CMake，Debug 构建未完成；机械方向、电流符号、边界位置、负载和温升仍需急停台架验证。

## 2026-10-05：最大限位被堵转锁存覆盖而输出零电流

- **现象**：轴到达软件最大限位后没有保持电流，最终日志可能仍显示堵转保持或输出许可为 0。
- **根因**：`gimbal_protection.c` 先处理 `STALL_HOLD`，此前累计的 Yaw 堵转锁存会在 `limit_hold_active` 到达输出分支前直接禁止发送；已知软件边界被动态堵转状态覆盖。
- **修复**：反馈在线且控制器确认最大/最小限位保持时，保护层先清理残留堵转候选/锁存并允许限位保持；反馈掉线仍从入口直接走零输出。驱动和控制器的最大限位方向保持逻辑不变。
- **验证**：Debug 增量构建和 `git diff --check` 通过；最大限位实际保持电流、反馈掉线清零和电机温升仍需上板观察。

## 2026-10-05：软件限位清零导致 Pitch 炮管掉落

- **现象**：通过遥控器把 Pitch 推到软件下限后，日志进入限位保持但实际输出电流为 0，松开摇杆后炮管因重力掉落；Yaw 到达边界也存在同样的零输出行为。
- **根因**：`gimbal_control` 在边界把速度目标置零，`gimbal_protection` 对软件限位默认禁止输出，`Gm6020_SetCurrent()` 和 `Gm6020_SetOutputEnabled()` 又拒绝限位状态下非零电流，三层共同把限位状态变成零电流。
- **修复**：为 Pitch/Yaw 增加独立最小/最大限位保持电流；控制器在边界直接生成保持分量并绕过 Ramp，保护层允许该专用输出，GM6020 增加 `Gm6020_SetLimitHoldCurrent()` 作为限位状态唯一非零入口。回中/命令超时继续保持，反馈掉线仍立即清零，明确向内命令同周期清锁并恢复闭环。
- **当前起点**：Pitch 最小/最大为逻辑 `+7000/+7000`，Yaw 最小/最大为逻辑 `-7000/+7000`，均不超过对应 `MAX_CURRENT_RAW=7000`；该电流只为防止位置突变的台架起点，长时间堵转温升和机械冲击仍需实测。
- **防复发检查**：限位日志必须同时显示保持目标电流、实际发送电流、输出许可、CAN 提交、反馈年龄和在线状态；测试反馈掉线、回中、向外继续推、向内脱离及双轴聚合槽位，不能只看“软件限位保持”阶段名。
- **补充修复**：保护层在明确向内命令时必须把 `allow_output` 置为真，限位解除与闭环电流提交不能隔着一个零电流周期；反馈恢复若仍在限位也直接重建保持，非限位恢复才先安全清零。
- **本次行为调整**：边界恰好到达时继续使用轴配置的限位保持电流并屏蔽外向命令；反馈坐标轻微超过边界时不再固定顶住，而是把位置目标钳在边界，继续运行位置/速度环输出内向纠偏，避免越界后的静态误差无法收回。
- **验证结果与待验证项**：已完成 Debug clean 构建和 `git diff --check`；实际限位方向、7000 原始值温升、机械端承受能力及断反馈停机仍需带急停上板验证。

## 2026-10-05：Pitch 目标中心方向反接并补充位置环 I/D

- **现象**：Pitch 默认在物理下限，固定目标设为中心角度时，实际角度没有向中心增加，反而继续向下；位置环只有 P，无法用位置误差变化率提供阻尼。
- **问题位置**：`Core/Inc/task/task_pitch/task_pitch_config.h` 的 `PITCH_MOTOR_CURRENT_SIGN`，以及 `Core/Src/app/gimbal/gimbal_control.c` 的位置环速度目标计算。
- **根因与依据**：最新上板动作显示 `PITCH_MOTOR_CURRENT_SIGN=+1` 才能把实际角度从下限抬向目标，改为 `-1` 会触发软件堵转；此前把电流方向和反馈转速方向错误地共用一个符号。位置环此前只有 P，重力静差也缺少可控的 I 补偿和 D 阻尼。
- **修复方法与行为变化**：Pitch 电流方向恢复为 `+1`，新增独立 `PITCH_FEEDBACK_SPEED_SIGN=-1`，只把原始转速映射到连续角度逻辑方向；位置环增加可配置 `position_ki_rpm_per_raw_s`、积分限幅和 `position_kd_rpm_s_per_raw`。Pitch 起始值为 `KI=0.002`、积分上限 `20 rpm`、`KD=0.005`，Yaw 的位置 I/D 保持关闭。I 在堵转保持、保护解除和反馈恢复时清零，避免解除后冲击。
- **防复发检查**：方向修改必须在急停台架验证“逻辑正电流最终是否使角度增加”，不能只凭宏名推断；I 应观察静差、电流和积分是否到限，KD 应观察测速噪声、过冲和电流饱和，不能把速度环 D 与位置环 I/D 混为一谈。
- **验证结果与待验证项**：已完成参数和符号静态检查；目标中心从下限向上运动、重力负载下的 I/KD 稳定性和最终物理电流仍需上板确认。

## 2026-10-05：Pitch 端点附近堵转保持无法解除

- **现象**：发射云台固定目标角度测试持续打印“堵转保持”；触发位置 8161，软件下限 8136，堵转方向为 +1，候选时间在锁存后仍继续增长。
- **问题位置**：`Core/Src/app/gimbal/gimbal_protection.c` 的堵转锁存和固定目标释放判据。
- **根因与依据**：锁存堵转时没有清除候选标志，诊断把已确认状态显示成仍在累计；固定目标释放同时要求反向移动 114 计数且仍在 `(min,max)` 内，触发点距下限只有 25 计数，反向移开必然越过下限，条件永远不成立。

## 2026-10-05：DBUS 拨杆保留值误丢弃右摇杆帧

- **现象**：DBUS 的右摇杆不能稳定控制云台；参考工程能够收到 18 字节帧，但当前适配层的拨杆字段校验会把部分帧判为无效。
- **问题位置**：`Core/Src/bsp/dbus/dbus.c` 的 `Dbus_DecodeFrame()`。
- **根因与依据**：参考工程把 `switches[0]`（日志中的左侧 S1）定义为 `DATA[5]` bit6~7，把 `switches[1]`（右侧 S2）定义为 bit4~5；同时当前代码在拨杆值为保留值 0 时直接丢弃整帧，连带丢弃 CH0/CH1 右摇杆数据。
- **修复方法与行为变化**：按参考工程的 S1/S2 位序解码 `DATA[5]`，拨杆值 0 只保留在诊断字段，不再阻断通道解码；CH0/CH1 仍按 11 位范围校验，帧错位时继续拒绝。
- **防复发检查**：以后修改拨杆逻辑时必须以参考工程的 S1=bit6~7、S2=bit4~5 为准；拨杆/鼠标不是当前云台输入有效性的门槛，不能因为保留值丢弃同一帧的摇杆。
- **验证结果与待验证项**：已完成源代码静态检查和拨杆位组合核对；ARM GCC 增量构建待执行，实际遥控器拨杆状态和右摇杆控制仍需上板确认。

## 2026-10-05：电机聚合发送未统一检查反馈新鲜度

- **现象**：GM6020/C610 的任务通常会调用 `Process()`，但驱动公开的发送入口仍可能在调用者漏掉该步骤时按旧的 `output_enabled` 和目标电流提交 CAN 帧；C610 聚合槽位读取和提交之间也没有屏蔽 CAN ISR/任务切换。
- **问题位置**：`Core/Src/bsp/gm6020/gm6020.c` 的 `Gm6020_SetOutputEnabled()`/`Gm6020_SendLocked()`，`Core/Src/bsp/c610_m2006/c610_m2006.c` 的 `C610_M2006_SendAll()`。
- **根因与依据**：输出许可、反馈时间戳和目标电流是并发状态；仅靠任务约定先调用 `Process()` 不能成为驱动层安全边界。C610 逐槽构建时若被 CAN ISR 打断，聚合帧可能混合不同时间点的状态。
- **修复方法与行为变化**：GM6020 使能和聚合发送都要求首帧/反馈年龄仍新鲜；C610 聚合发送在短 PRIMASK 临界区内读取所有槽位并提交，且同样在提交时检查反馈新鲜度；临界区不等待、不打印，CAN 邮箱不足仍返回失败。
- **防复发检查**：所有电机驱动的 `SetOutputEnabled`、聚合发送入口都必须独立检查反馈有效性和年龄；读取全部槽位、构建数据、提交 HAL 邮箱必须作为一个短事务，不能只在上层任务中口头保证调用顺序。
- **验证结果与待验证项**：已完成 ARM GCC/CMake Debug 全量构建；反馈中断与发送任务的精确交错、掉线后电调实际零电流和邮箱拥塞行为仍需 CAN 台架验证。

## 2026-10-05：CubeMX 重新生成覆盖 DBUS 专用接收路径

- **现象**：本次重新生成虽已出现 `USART3_IRQHandler()`，但生成入口调用了 `HAL_UART_IRQHandler(&huart3)`；同时 `.ioc`/`usart.c` 又恢复了不需要的 PC10 TX。HAL 的单缓冲接收状态机与 DBUS 自定义 DMA 双缓冲会争用 USART3/DMA 状态，PC10 也会造成配置和实际接线不一致。
- **问题位置**：`yuntai.ioc` 的 PC10/NVIC/引脚列表、`Core/Src/usart.c` 的 USART3 MSP、`Core/Src/stm32f4xx_it.c` 的 `USART3_IRQHandler()`。
- **根因与依据**：CubeMX 生成的默认 USART IRQ 只适合 HAL UART 接收 API；本工程由 `Dbus_USART3_IRQHandler()` 直接处理 IDLE、帧间边界和 UART 错误，DMA 完成则由 `DMA1_Stream1_IRQHandler()` 进入双缓冲回调。DBUS 只使用 PC11 RX，不能仅凭生成器出现 USART3 就认为专用接收链路完整。
- **修复方法与行为变化**：`.ioc` 固定为 PC11-only、异步 RX、100000 baud、9B+偶校验、DMA1 Stream1 循环模式，并保留 USART3 IRQ 优先级 5；MSP 只初始化/释放 PC11；USART3 IRQ 改为只调用 `Dbus_USART3_IRQHandler()`，并在生成处理器的用户代码区保留禁用 HAL 默认调用的保护，避免下次重新生成后重新争用 DMA；同时 DBUS CH4 滚轮按 11 位掩码解析，避免保留位污染数值。
- **防复发检查**：每次 CubeMX 重新生成后必须同时核对 `.ioc`、`huart3` 初始化、PC11 GPIO、DMA1 Stream1、USART3 IRQ 和 DBUS 自定义钩子；看到 `HAL_UART_IRQHandler()` 不能视为 DBUS 已接通；重新生成后还要确认 USART3 处理器中的保护仍在。协议字段按位宽掩码后再转换，不能直接把 16 位存储单元当成 11 位字段。
- **验证结果与待验证项**：已用 ARM GCC 完成 `cmake --preset Debug` 和 `cmake --build --preset Debug` 全量构建，生成的 ELF 通过链接；DBUS 信号电平、帧同步、摇杆方向和 CAN/电机实机行为仍需上板验证。

## 2026-10-04：DBUS 的 `.ioc` 同步 USART 与异步 DMA 实现不一致

- **现象**：`.ioc` 把 USART3 配置为同步模式并占用 PC10/PC12，生成代码使用 `USART_HandleTypeDef husart3`；DBUS 驱动却按异步 UART 的 `huart3`、IDLE 中断和 DMA 双缓冲寄存器运行，重新生成或直接构建都会导致句柄/初始化路径不一致。
- **根因与依据**：同步 USART 的 HAL 初始化是 `HAL_USART_Init()`，异步接收 DMA 需要 `HAL_UART_Init()`；启用偶校验时仍要用 9B 才能保留 8 位 DBUS 数据。DBUS 只接收 PC11，不需要时钟和发送引脚。
- **修复方法与行为变化**：`.ioc` 改为 `VM_ASYNC`、9B+偶校验、仅 PC11 RX；源代码统一为 `UART_HandleTypeDef huart3`、`HAL_UART_Init()`、`MX_USART3_UART_Init()`，并保留 DMA1 Stream1 循环双缓冲和 USART3 IDLE/错误中断钩子。
- **防复发检查**：修改 UART 的同步/异步、校验或数据位时，同时核对 `.ioc`、句柄类型、初始化函数名、MSP GPIO、DMA 方向、IRQ 入口和调用方；异步 UART 重新生成后不能继续保留 `husart*`/`HAL_USART_*`。
- **验证结果与待验证项**：ARM GCC/CMake Debug 全量构建通过；CubeMX 图形界面重新打开并生成一次、DBUS 接收器电平和实机帧质量仍需上板确认。

## 2026-10-04：C610 在线 API 会在漏调用 Process 时永久保持在线

- **现象**：`C610_M2006_IsOnline()` 只读取状态和首帧标志，不重新比较反馈年龄；如果上层漏调用 `C610_M2006_Process()`，旧反馈会一直报告在线。
- **根因与依据**：在线状态的安全含义是“最近一帧反馈未超过配置的 HAL 毫秒超时”，不能把任务调度调用当作唯一超时检查点。
- **修复方法与行为变化**：`IsOnline()` 现在用 `HAL_GetTick()` 直接计算反馈年龄，未来时间戳按回绕/中断竞态安全处理；`Process()` 仍负责清零目标和关闭输出。
- **防复发检查**：凡是公开的 `IsOnline`/`IsReady` API 都要独立验证时间有效性；状态刷新函数用于执行安全动作，不能替代查询函数的基本安全条件。
- **验证结果与待验证项**：Debug 全量构建通过；反馈停止后的实际停机时延仍需在 CAN 台架测量。

## 2026-10-04：C610 超时检查把 ISR 新时间戳下溢当成掉线

- **现象**：任务把当前 HAL 时间传给 `C610_M2006_Process()` 的同时，CAN ISR 若刚写入更新的反馈时间戳，无符号相减会得到接近 `2^32` 的大值，偶发立即进入离线并清零输出。
- **根因与依据**：任务时间和 ISR 时间来自同一个 HAL 毫秒时基，但读取存在先后竞态；只有差值不超过半个无符号范围时才可解释为正常经过时间。
- **修复方法与行为变化**：仅当 `elapsed_ms <= INT32_MAX` 且达到超时阈值才判定掉线；未来时间戳按新反馈处理，下一周期重新检查。
- **防复发检查**：所有“任务当前时间 − ISR 写入时间戳”的超时判断都要处理未来时间戳和 Tick 回绕，不能只依赖无符号减法。
- **验证结果与待验证项**：Debug 全量构建通过；中断与任务精确交错的时序需在目标板或主机仿真进一步覆盖。

## 2026-10-04：GM6020 快照在线标志未排除已离线状态

- **现象**：快照在线字段只看反馈年龄；在驱动已进入 `OFFLINE` 后，极长时间 Tick 回绕的边界或调用顺序可能让年龄条件再次成立，给上层一个错误的在线状态。
- **根因与依据**：在线是“收到过反馈、状态未离线、年龄在有效窗口内”的合取条件，单独比较时间差不能覆盖状态机已经执行的安全停机。
- **修复方法与行为变化**：`Gm6020_GetSnapshot()` 现在同时排除 `OFFLINE`/`UNINITIALIZED` 状态，再计算反馈年龄。
- **防复发检查**：快照里的 `online` 必须同时核对首帧标志、状态机安全状态和同一 HAL 时基的年龄；Tick 回绕处理不能绕过已锁定的离线状态。
- **验证结果与待验证项**：Debug 全量构建通过；长时间 Tick 回绕与真实 CAN 断线恢复仍需仿真/上板验证。

## 2026-10-04：C610 可在没有新鲜反馈时打开输出

- **现象**：`C610_M2006_SetOutputEnabled(true)` 过去只检查句柄是否注册；首帧尚未到达或反馈已超时时，上层仍可打开输出并把目标电流交给聚合发送。
- **根因与依据**：输出许可没有绑定 `feedback_received` 和反馈年龄，导致“没有确认电机仍在线”也能发送非零电流。
- **修复方法与行为变化**：打开输出前调用在线安全门；未收到过反馈、已超时或状态离线时返回 `false`，只有新鲜反馈才允许进入运行状态。
- **防复发检查**：所有电机驱动的输出使能路径都要检查首帧标志、状态和反馈超时；`SetCurrent()` 成功只代表缓存，不得绕过 `SetOutputEnabled()` 的安全门。
- **验证结果与待验证项**：Debug 全量构建通过；断线时的 CAN 发送时序和电调实际零电流仍需台架验证。

## 2026-10-04：C610 多字段反馈复制可能混合两帧

- **现象**：供弹日志调用 `C610_M2006_GetFeedback()` 时，CAN ISR 可能正依次更新角度、转速和电流，直接结构体复制会把不同反馈帧拼到同一条日志。
- **根因与依据**：`volatile` 只能保证单次字段访问可见，不能让多字段复制原子化；C610 反馈和任务日志运行在不同上下文。
- **修复方法与行为变化**：增加 `feedback_sequence` 奇偶序列号；ISR 在整帧更新前后递增，任务复制前后核对一致性，连续冲突时返回 `false` 并等待下一周期。供弹运行时在快照失败时跳过该条反馈日志，不把零初始化内容打印成真实反馈。
- **防复发检查**：所有 ISR 写、任务读的多字段反馈都必须通过序列号、临界区或队列形成快照；失败快照不能拿来刷新保护/在线证据或打印成正常帧。
- **验证结果与待验证项**：Debug 全量构建通过；高频 CAN 与任务同时访问的冲突概率和实机日志仍需仿真/上板验证。

## 2026-10-04：Yaw 位置增益单位误用导致速度请求过早饱和

- **现象**：用户提高位置 P 后响应改善不明显，目标附近持续抖动；本轮初次读取配置时 `YAW_POSITION_KP_RPM_PER_RAW=10`，速度上限为 40 rpm。
- **问题位置与依据**：`task_yaw_config.h` 的增益及 `GimbalControl_Update()` 的速度生成/限幅。P 的单位是 rpm/计数；10×4 计数就达到 40 rpm 上限（约 0.18°），继续提高增益只会压缩渐进减速区。该饱和阈值由实现确定；本轮未提供对应新日志，不能把所有抖动归因于此。
- **修复与防复发**：先恢复合理量级的位置 P，并在配置与任务文档增加单位、1°/30°示例和饱和阈值说明；先定位速度或电流是否饱和，再单独调环路。速度 P 同时提供制动，不能未经实测就声称降低它一定减少抖动。
- **验证范围**：核对实际控制公式及限幅；机械负载、到位时间和抖动改善待重新烧录后的日志验证，构建结果在交付时单独报告。

## 2026-10-03：双轴硬件测试绑定 Yaw 且反馈快照混用

- **现象**：GM6020 标定和角度环测试只能接入 Yaw；角度测试控制后又重新读取驱动状态，日志可能把不同反馈周期的数据放在一起。
- **根因**：测试接口直接依赖 `YawTask_RuntimeTypeDef`，日志计时使用文件级全局变量，Pitch 没有可复用的正式运行时。
- **修复方法**：新增 `app/gimbal/gimbal_axis` 轴无关运行时；测试参数和日志状态按轴传入；运行时把唯一快照复制到输出结构，测试日志直接引用该快照。Pitch 使用独立 GM6020 ID `0x206`、配置和实例。
- **防复发检查**：测试不能包含第二套 PID/Ramp/保护；每周期只能调用一次快照并贯穿控制、保护、日志；禁止从句柄字段逐项读取反馈。
- **周期输出处理**：保护根据本周期计算出的驱动力请求判断启动和堵转，禁止复用快照中旧输出许可；日志的许可与保护后目标电流来自本周期结果。
- **验证结果与待验证项**：两轴标定、角度环和关闭测试三种编译分支均通过；临时主机程序编译实际驱动/算法/运行时，验证双轴槽位、连续角度、快照竞争与失败、目标越界零输出。双轴电机接线、角度方向、边界和实机恢复仍待台架验证。

## 2026-10-03：固定目标堵转被零命令误解除

## 2026-10-03：串口 DMA 缓冲区竞争与中文长度回绕

## 2026-10-03：电机型号电流范围混用

- **现象**：Pitch 到达最大软件限位后，输出电流突然变为 0，位置保持丢失。
- **根因**：控制器固定限位电流、`gimbal_protection` 动态状态和 GM6020 驱动二次方向拦截叠加；任一层进入锁存后都会覆盖闭环计算，最终发送零电流。
- **修复**：删除动态堵转/锁存和固定限位电流路径。驱动只报告当前边界；控制层过滤继续向外的命令，保留角度环、速度环、Ramp 和抗重力补偿，反向命令同周期生效。
- **防复发检查**：边界处不得调用固定保持电流接口、不得把软件限位原因转换为零输出；驱动 `SetCurrent` 不得按边界方向拒绝上层闭环电流。
- **验证结果**：GM6020、Yaw/Pitch 运行时和供弹运行时已通过 ARM GCC `-fsyntax-only -Wall -Wextra -Werror` 静态检查；CMake 未安装，未完成 Debug 构建；边界方向、电流符号和温升仍待上板实测。
